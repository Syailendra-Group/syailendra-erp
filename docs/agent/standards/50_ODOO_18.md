# Odoo 18 Community Standards

## Model and ORM

- Follow Odoo 18 CE APIs and the project's addon layout; verify behavior against the
  official 18.0 documentation and installed source before relying on a feature.
- Use the ORM (`search`, `search_count`, `search_read`, `create`, `write`) rather than
  direct SQL for application operations. SQL is reserved for controlled admin scripts
  and migrations with explicit review.
- Operational list endpoints must paginate and filter server-side; do not fetch an
  unbounded model set into the browser.
- Batch ORM work to avoid N+1 queries. Declare indexes only for measured query paths.
- Keep business invariants in model constraints and state-transition methods, not only
  in UI forms.
- Use `@api.constrains` for cross-field checks and SQL constraints for uniqueness
  where appropriate; provide useful translated `ValidationError` messages.

## Security

- Every new model needs `ir.model.access.csv` entries and relevant record rules.
- Default to least privilege, explicit groups, company scoping, and no public ACL.
- Avoid `sudo()`; where unavoidable, scope the record set and document the reason.
- Use ORM domains with company context. Never trust a client-supplied `company_id`
  without checking the active user's permitted companies.
- Do not expose model RPC directly to anonymous/public clients.

## Lifecycle and migrations

- State changes must go through explicit methods with authorization and validation.
- Do not delete traceability records; use archive or documented disposition to retain
  lineage and audit evidence.
- Bump addon version and add an upgrade migration for data/schema transformations.
- Odoo CE does not provide Enterprise-only `quality_control`; the project uses a
  custom QC model plus warehouse quarantine routing.
- For live Odoo CLI upgrades, use `--http-port 8079 --stop-after-init` to avoid the
  running web process port collision; restart the container only after successful
  upgrade and verification, with explicit deployment authorization.
