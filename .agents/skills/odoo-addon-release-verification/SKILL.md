# Odoo Addon Release & Verification

## When to Use

Use when shipping or upgrading a custom Odoo addon on a Dockerized host and you must prove the release actually landed and works — deploy, `-u` upgrade, `--test-enable` run, or ACL grant. Provisioning a brand-new stack, database migration, and reverse proxy belong elsewhere.

## Pre-flight (before Procedure step 1)

1. **Establish how the deployed addon actually gets there.** `ls -la <host addons dir>/<module>` and check for a `.git` directory: a clone means `git pull` is the deploy step, a plain tree means a manual file copy is the only path — do not assume a VCS sync exists. Read the deployed `__manifest__.py` version and the DB's `ir_module_module.latest_version` for that module; if they disagree you are shipping on top of an unknown state, so resolve that first.
2. **Test new code in an isolated staging addons path before it reaches production.** Copy the module and its custom sibling dependencies into a container-visible staging directory; generate a restricted config from the production config with `addons_path` listing only staging and core addons. Set both `ODOO_RC` and `-c` to that staging config, use a clone DB with disabled automation and isolated data/filestore, and omit the deployed addon directory entirely. Verify the effective `addons paths:` and module `__path__` plus a test that asserts a symbol unique to the change is loaded; duplicate module trees do not reliably shadow one another.
3. **Back up the deployed addon directory itself before overwriting it** (`cp -a <host addons dir>/<module> /home/deploy/backups/addon_<module>_<oldversion>_<stamp>/`): the rollback artifact must not depend on Git history existing on the deploy host — a plain-copy deploy dir has no `.git`, and those old files are the only way to restore the previous runtime without a full DB restore.

## Procedure

1. **Prove file parity before touching runtime.** `md5sum` the changed files in the repo and in the container addon path; do not upgrade a copy you have not verified. Aggregate `md5sum` over all files if the module is large.
2. **Back up the database first.** `pg_dump -U odoo -Fc -d <db> > <db>_pre_<change>.dump` run as the DB superuser the container expects (often `odoo`, not `postgres`).
3. **Deploy into the container.** Stage on the host, then `docker cp` → `cp -r` into `/mnt/extra-addons/<module>/` → `chown -R $(docker exec <container> id -u odoo):$(docker exec <container> id -g odoo) /mnt/extra-addons/<module>/`. Bind-mounted addon directories are usually not writable by the deploy user, and the container's `odoo` uid is not always 100. When the mount source is a host directory (see pre-flight step 1), write it on the host directly and skip the `docker cp` round-trip. If the deploy user cannot sudo and the addon directory is owned by another uid (mode 755), write through a privileged container instead: stage the copy on the host, then `docker run --rm -v <addons>:/mnt -v <stage>:/src <image> sh -lc 'cp -a /src /mnt/<module> && chown -R <uid>:<gid> /mnt/<module>'`. The host-side owner may display as an unrelated system user — that is the container uid/gid mapped to host names; verify ownership by effect (the container user can read the files), not by the displayed name.
4. **Upgrade without colliding with the live web port.** `odoo -u <module> -d <db> --http-port 8079 --stop-after-init --log-level=warn`. Always pass `--http-port 8079 --stop-after-init`; otherwise the second Odoo process dies with `[Errno 98] Address already in use` on 8069.
5. **Run tests on a clone database, never production.** `odoo -u <module> -d <db>_test --test-enable --http-port 8079 --stop-after-init --log-level=info > /tmp/test.log 2>&1`. Create the clone from the fresh dump with `createdb -U odoo -T template0 <db>_test` then `docker exec -i <db-container> pg_restore -U odoo -d <db>_test --no-owner < <dump>`, and verify record counts in the clone match production before upgrading it. Restore into a NEW database name and leave existing clones in place — they are the state your earlier numbers came from. Walk the full recipe in `references/isolated-clone-staging.md`, including how to give the clone its own data dir and filestore.
6. **Read the pass line from `odoo.tests.result`, not only `tests.stats`.** Odoo 18 prints `odoo.tests.stats: <module>: N tests <t>s <q> queries` and then `odoo.tests.result: X failed, Y error(s) of K tests`. The two counts can legitimately disagree — the stats line counts suite-level test objects while the result line counts executed test methods (observed `63 tests` against `0 failed, 0 error(s) of 53 tests` in the same run). Quote both numbers instead of collapsing them into one, and take the verdict from `tests.result` (`0 failed, 0 error(s)`) together with the absence of `FAIL`/`ERROR` in the log. A `Ran N tests` line may not appear at all.
7. **Restart and health-check.** `docker restart <container>`, then `curl -s -o /dev/null -w '%{http_code}' http://localhost:8069/web/login` must return `200`.
8. **Verify permissions by effect, not by rows.** Having `ir_model_access` rows and a group membership proves configuration, not access. Probe each model with the integration account over JSON-RPC (`search_count`) and confirm it returns a number instead of `AccessError`.
9. **Identify the real caller.** Read the frontend/service layer to see which Odoo account its env credentials belong to. Granting a read-only group is meaningless if that account is an admin user — report it as a least-privilege finding, do not claim the restriction works.
10. **Prove the committed tree matches the runtime.** Compare the file list in git (`git ls-tree -r origin/main --name-only addons/<module>`) with `find /mnt/extra-addons/<module> -type f`, then re-check the aggregate `md5sum`. A module can boot on the server while a package `__init__.py` is missing from git — the deploy copied it, the commit did not — and a fresh install fails later.

- **A schema that is ahead of the deployed addon path breaks every CLI entry point, including `odoo shell`.** After upgrading a clone with a staged addons path, the clone's columns match the staging code while `/mnt/extra-addons` still holds the old module. Any later `odoo shell -d <clone>` or `-u` run loads the OLD code from the default path, declares fields whose columns the migration already dropped, and dies during environment init (`column res_partner.x does not exist`) before your first statement executes — passing `--addons-path` on the same command line does not reliably rescue it. Treat such a clone as usable only through the exact staged invocation that created it, or re-sync the deployed addon first; do not read the crash as a model bug.
- **A frontend build must never outrun the addon upgrade it depends on.** When new UI reads fields or models that only exist in the newer addon, serving that build against the old schema breaks those pages even though the app boots and unauthenticated routes still answer 200/307 (the auth proxy hides the failure behind a redirect, so HTTP status cannot prove route health). Release the addon upgrade and the frontend build together, and verify through an authenticated request rather than a status code.
## Pitfalls

- **Hierarchy checks must include archived children.** Traverse category relations with `active_test=False` in integrity constraints; default `child_ids` hides archived rows and lets a parent with only archived children gain a parent, silently creating a third level. Prove the fix with a regression that archives a child, expects re-parenting the root to fail, and preserves Odoo's recursion checks.
- **Approval expiry is a stop-gate, even after an earlier broad execution approval.** If a deployment tool request times out awaiting approval, do not retry it, split it into smaller commands, or invoke another tool to reach the same side effect. Report tested source versus live hashes and ask for fresh approval separately.
- **A Python ORM constraint is not a SQL constraint.** `@api.constrains` protects ORM create/write/import paths when its trigger fields are present; raw SQL bypasses it. A category hierarchy constraint does not also enforce which category IDs a partner may be tagged with—test and report those two invariants separately.
- **`odoo shell` rolls back on exit unless the script commits.** A data script that prints `APPLIED ...` and then exits normally changes nothing: Odoo's shell does not commit automatically. Always call `env.cr.commit()` after the writes and then re-read the row from PostgreSQL — the printed success line is not evidence. A script that writes an artifact file *before* its write loop also loses the artifact path when that path does not exist inside the container (`/home/deploy/...` on the host is invisible in the container): write artifacts to a container path and `docker cp` them out.
- **A staging addons path that still contains the production addons dir does not shadow the deployed module.** Copying the module to a scratch path and then passing `--addons-path=<stage>,<prod-addons>,<core>` leaves two copies of the module resolvable, and the deployed one can win, so the staged code silently never loads and the test suite reports a clean, wrong run. Copy the custom sibling addons the module depends on into the stage instead (omit the production addons dir), point `ODOO_RC`/`-c` at a staged config so the deployed `odoo.conf` cannot re-inject its own `addons_path`, and add one test that asserts a symbol unique to the change exists on the model — that assertion is what makes the wrong-tree case fail loudly.
- **A bind-mounted addon directory is not writable by the SSH deploy user.** It is owned by the container's odoo uid (often `100:101`, displayed on the host as unrelated system users), so a plain `cp` into it fails with `Permission denied` while the subsequent `-u <module>` run still exits `0` serving the OLD code. Write through a privileged container instead: `docker run --rm -u 0 -v <addon-subdir>:/target -v <stage>:/src:ro <odoo-image> sh -lc 'cp /src/<file> /target/ && chown -R 100:101 /target'`. Then prove parity with `md5sum` on both sides plus a model-level check (`hasattr(model, '<guard>')`) — never infer deployment from the upgrade exit code.
- **Deploying a subset of files while the repo manifest version has moved on is a valid, safer deploy.** When other actors hold uncommitted work in the same module (new models, a newer `migrations/<ver>/`), copying the whole source tree installs their in-flight migrations too. Copy only the touched files and leave the deployed `__manifest__.py` at its installed version: `-u <module>` still reloads the Python code, while migrations for the newer version never run because the DB version equals the manifest version.
- `grep -cE "^ERROR" log` exits `1` when the count is zero. Use the printed count, never the exit code, to judge a clean run.
- Upgrade exit `0` is not proof: grep the upgrade log for `ERROR|CRITICAL|Traceback` as well.
- `res.users` uses `groups_id` in Odoo 18, not `group_ids`. A wrong field name in a data XML fails silently or aborts the load.
- Re-applying a data file with `noupdate="1"` will not update existing records; drop `noupdate` for idempotent grants, and fall back to SQL only when the XML path is unconfirmed.
- Granting an admin uid to a group proves nothing about a real integration account; probe with the credential set actually used in production.
- Delete `*.orig` and `__pycache__` before staging. They are deploy leftovers, and `git add -A` sweeps them into history.
- Exclude `__pycache__` on both sides of an aggregate md5 comparison, otherwise hashes differ for reasons unrelated to source.
- `docker exec` needs `-i` when the command reads stdin (a heredoc or pipe for SQL/scripts). Without it the command gets empty stdin and can exit `0` while printing nothing — a silent false negative that reads like "0 rows" rather than an error. Then verify the row count, not just the exit code.
- `docker exec -i` nested inside a script that is itself piped to `bash -s` swallows the rest of that script: the first `-i` call takes the script text as its own stdin, every later command never runs, and the session still exits `0` with truncated output. Put the script in a file on the target (`ssh host 'cat > /tmp/x.sh'`, then `ssh host 'bash /tmp/x.sh'`) and add `</dev/null` to each `docker exec -i` whose stdin you do not actually want to forward.
- After copying a fixed file to a staging path, prove it arrived (`docker exec <c> grep -c <unique token> <path>`) before re-running the test. A failure that repeats identically after a "fix" almost always means the file never landed: a tarball built from the repo root carries the `<module>/…` prefix, so extracting it into the module's own staging dir writes `<module>/<module>/…`. Build the archive from the module's parent directory so the archive root matches the destination.
- `psql -U <user>` with no `-d` connects to a database named after the user, which normally does not exist (`FATAL: database "odoo" does not exist`). Always pass `-d <db>`, and `-d postgres` when listing databases.
- Quote psql field separators when they travel through nested SSH/docker quoting — `-F'|'`, never `-F|`: an unquoted pipe is parsed as a shell pipe, so the command fails or misparses before psql ever sees it.
- **A new fail-fast guard turning previously green tests into errors means the tests encoded the old contract.** Rewrite the fixtures to create prerequisites before the guarded call and move each refusal assertion to the point it now fires; never weaken an assertion or delete the test to restore green.
- A failing addon test is not automatically a failing model. A field with `compute=` and no `store=True` is cached per environment, so when the compute reads another model (`search_count` on `res.partner`, a related count) a record created later in the same test does not invalidate it and the assertion reads the pre-change value. Refresh with `record.invalidate_recordset(['<field>'])` before asserting; production recomputes per request, so the displayed value is correct. Never relax the assertion to match the stale value.
- When the final parity step finds a file missing from a commit that is not yet pushed, fold it into the right commit with `git commit --fixup=<sha>` then `GIT_SEQUENCE_EDITOR=true git rebase --autosquash -i <sha>^`; a separate "add missing file" commit leaves the bad commit broken if anyone checks it out.
- Staging directories left in the container by earlier sessions may be root-owned; a plain `docker exec <c> rm -rf` fails with Permission denied and, under `set -e`, silently aborts the remaining cleanup. Clean them with `docker exec -u 0 <c> rm -rf ...`.
- Odoo translated columns are plain `Char` on custom models and JSONB on core ones — `name->>'en_US'` raises `operator does not exist` on a Char column. Check `information_schema.columns` for the column type before writing a verification query.
- When a completion notification for a long job never arrives, do not assume the job finished or failed: check the log's mtime and `pgrep` for the process. A log whose last write predates the change timestamp contains only historical entries — cite it with that caveat, never as evidence of current behavior.
- **A DB container cannot see the host backup directory.** `docker exec <db> pg_restore --list /host/path/<dump>` fails on the missing path, and with `2>/dev/null | wc -l` that failure reads as **`0` entries** — a false "corrupt or empty archive" verdict that sends you chasing a healthy dump. Always pipe it: `docker exec -i <db> pg_restore --list < <dump>`. Treat a container-side `0` as a failed inspection, not as a property of the dump.
- **A `--list` TOC is not a restore test.** It proves the archive parses; it validates no row, no constraint, and no migration state. Prove a dump by restoring it for real into a new database and comparing the same aggregates on both sides (source vs restored), keeping the restore log path in the report.
- **Verify the deployed addon directory, not just the DB.** Before overwriting `/mnt/extra-addons/<module>`, snapshot it on the host (`cp -a`) — a plain-copy deploy tree has no `.git`, so those files plus the DB dump are the entire rollback set.
- **Give a staging clone its own `data_dir` and filestore, and disable its automation.** Copy the production filestore into the staging data dir so attachment/image reads resolve, and set `max_cron_threads=0` plus `http_enable=False` on the clone config — otherwise the clone's scheduled jobs run against real recipients while you test. Neutralise the clone's `ir_cron` rows in SQL as well (`UPDATE ir_cron SET active=false`).
- **Generate the staging config from the production `odoo.conf` programmatically,** using `configparser` and writing it with `os.open(..., O_CREAT | O_EXCL, 0o600)`; a hand-written config drifts from the deployed one, and the `addons paths:` line at the top of the run log is the only proof of which tree actually loaded.

## Verification Helper

Run `scripts/check_test_log.sh /tmp/test.log <module>` after a test run. It prints the `tests.stats` line, counts real ERROR lines, and exits non-zero when the run is dirty — use it instead of eyeballing truncated terminal output.
